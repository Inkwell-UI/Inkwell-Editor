# Deploy and Package Mod (`src/main/deploy`, `src/renderer/shell/DeployMenu.tsx`)

UX spec 4.1. The top bar `Deploy` dropdown lists targets with their exact folder (MO2 mod folder, MO2 overwrite, Vortex, Package Mod); `Build All` stays separate. The Package Mod and Vortex rows save the same files as one zip (see Package and Vortex below).

## Targets (`plan.ts` `resolveTarget`)

- `MO2 mod folder`: `<mo2ModsDir>\<mod name>` (mod name setting, default the project name; no separators allowed). Without `mo2ModsDir`, an `mo2` preset in `project.json` (`deploy.path`) is the fallback.
- `MO2 overwrite folder`: `mo2OverwriteDir`.
- Both are set in the MO2 row of Settings (or `INKWELL_MO2_MODS`, `INKWELL_MO2_OVERWRITE`). The dropdown also chooses the scope: all SWFs, or only the active one.

## What is written (`planDeploy`, pure: project + settings -> file plan)

| SWF target | Files |
| --- | --- |
| `hudWidget` | `Interface\exported\widgets\<modId>\<Widget>.swf`, `Source\Scripts\*.psc`, and with a Papyrus compiler `Scripts\*.pex` and `<modId>.esp` (the `compileWidget` layout; widget name = SWF name with a capital) |
| `customMenu` | `Interface/Inkwell/<modId>/<Swf>.swf` (O2, unverified in game; the one constant is `menuSwfPath` in `src/shared/menu.ts`), `SKSE/Plugins/Inkwell/menus/<menuName>.json` (the Spec `MenuDef`, overwritten every deploy) and, once per mod, `SKSE/Plugins/Inkwell/<modId>.ini` (the commented default INI: **created if absent, never overwritten or retired, not in the manifest**). The dialog says "Requires Inkwell Runtime <min> or newer; not included in this deploy." (`<min>` = `projectMinRuntime`, 0.3.0 today) and explains the runtime check: once per mod (needs the Papyrus compiler) `Source/Scripts/<modId>_RuntimeCheck.psc`, `Scripts/<modId>_RuntimeCheck.pex` and `<modId>_RuntimeCheck.esp`, the in-game message when the runtime is missing or too old (`docs/menus.md`, Runtime check). **Package Mod / Vortex always include them for a menu mod** (mandatory; without a compiler the package is refused with `runtime-check-missing`, a folder deploy only warns). Inkwell.dll and Inkwell_API.pex are never written. Names, JSON, INI and lint: `docs/menus.md` |
| `menuReplacement` | skipped with warning `menu-replacement-skipped` |

Without a Papyrus compiler (setting or `INKWELL_PAPYRUS`) a widget is deployed as SWF plus `.psc` sources, with warning `papyrus-compiler-missing`. Only one `.esp` is generated per mod (a second widget warns `widget-esp-shared`).

## Dev deploy (0.3, Phase 6b; `docs/dev-mode.md`)

The Deploy menu has a **Dev deploy** checkbox (per project, user settings, off by default). On, a deploy to the **MO2 mod folder or overwrite folder** ships the custom menus' dev SWF (`build/<swf>.dev.swf`, the pin/watch hooks), writes `SKSE/Plugins/Inkwell/Inkwell.ini` with `[Dev] DevMode=1`, the project's token and the port (merged into an existing file, `devIni`/untracked: written when it differs, not in the manifest, never retired, listed in the dialog without the token) and afterwards sends `reload` to the connected game; the ack with its time appears in the status bar deploy item (`DeployState.hotReload`) and the toast. **Package Mod and the Vortex zip never contain dev mode, the token or the dev SWF** (`deploy/devDeploy.test.ts`). `DeployInput.dev` / `DeployDeps.dev()` carry it; `planDeploy({dev})` adds the INI only next to a custom menu.

## Rules

- **Never into the game's `Data` folder**: refused when the target is inside `<Skyrim>\Data` for any detected install, or matches `\Skyrim*\Data` by name (tested both ways). Nothing is compiled first.
- **Never outside the target folder**: every path (planned, and every path read from an older manifest) goes through `safeJoin` (no absolute or drive paths, `..`, empty parts, reserved characters). A bad SWF name fails the plan before any write.
- **Never unmodified vanilla files**: every `.swf` is hashed against the vanilla cache index (`isUnmodifiedVanilla`); a match refuses the whole deploy.
- **Menu files** (`run.ts`): a `customMenu` SWF's menu.json (or the defaults) becomes the JSON and the INI; `menuLint` rows join the gate (`menu-name-invalid`, `menu-name-duplicate`, `menu-hotkey-invalid`, `menu-event-invalid`, `menu-limit`: warning above 4 menus, error above 16, project-wide even for a one-SWF deploy; `menu-file-invalid` for an unreadable menu.json). A file entry with `createOnly` (the INI) is written only when it does not exist; `commitDeploy` reports it as `preserved`. A deploy that predates this layout retires its flat `Interface/<name>.swf` through the manifest like any other file.
- **Export gate** (`src/main/lint/gate.ts` `exportGate`, design spec "Severity levels"): the lint of the SWFs being deployed (scope: all, or the active SWF only) decides. Errors block, warnings deploy and are listed, info is never shown here; **Strict Mode** (`project.json` `strictMode`) promotes warnings to errors. The issues are, per deployed SWF: the compile lint (a `hudWidget` is compiled fresh by the deploy), the `unreachable-node` warnings of its IR, and for a `customMenu` the lint of its last build in this session plus `build-not-ready` (error) when it has not been built since the project was opened, is still compiling, or its last build failed. Plan notices (`papyrus-compiler-missing`, `widget-esp-shared`, `menu-replacement-skipped`) are deploy-level, listed as "Deploy notes" and never promoted. A SWF with errors contributes no files. A blocked prepare always opens the dialog (title `Deploy blocked`, `Blocked: N lint error(s)`, each row links to its layer: click cancels and selects it), with Deploy disabled and the reason; `commit` refuses a blocked token in main as well (never trust the renderer) and writes nothing. `image-missing-asset` during a first sync is an error like any other: wait for the assets, then deploy again.
- **First deploy to a new target asks**: the dialog shows the exact path and the file list (and files that will be removed, warnings, notes). The confirmation is remembered per project and folder in `settings.json` (`deployConfirmed`) after the first successful deploy.
- **Manifest** `.inkwell-deploy.json` (version, mod id, time, `files[rel] = { sha256, swf }`). A later deploy deletes only files named in the old manifest that this deploy no longer produces, and only if they are still byte-identical to what Inkwell wrote (a hand-edited file is kept and reported). Folders emptied by that are removed. Other files are never touched. An "active SWF only" deploy retires only that SWF's files.
- **Images**: in `imageMode: "dds"` each image a deployed SWF references is written as `textures/Inkwell/<modId>/<hash>.dds` (from `assets/<hash>.png`; a missing asset fails the prepare step before any write). They go through the same `safeJoin`, manifest and retirement rules; switching back to embedded retires them. Embedded mode adds no files. See `docs/images.md`.
- **Atomic-ish writes**: temp file in the same folder, then rename; identical files are not rewritten. The manifest is written last. All compiling and checking happens before the first write (`prepare`, then `commit`, so the confirmation can come between).

## Flow and feedback

`prepareDeploy(target, scope, activeSwf)` (IPC) compiles with the resident FFDec wrapper and the Papyrus compiler, checks, and returns the file list, the gate result (`gate: {ok, strict, blocking, warnings, info}`), the plan notices (`lint`) and `needsConfirm` (always true when blocked); `commitDeploy(token)` writes. Progress and the result are in `SyncUiState.deploy`: the status bar item (`Deploy: 856 ms [Compile 845 ms - Vanilla check <1 ms - Write 11 ms]`) and a toast with the counts. Compile errors (including Papyrus) are gate errors: nothing is written. A `customMenu` needs its SWF built in this session first (Build All); a missing build is a gate error that says so.

## Package Mod and Vortex (`service.ts` `writePackage`, `zip.ts`)

- **Same planner, same gate.** `prepare('package' | 'vortex', scope)` runs the exact `prepareDeploy` of an MO2 deploy (same file plan, compile, export gate, Strict Mode, vanilla refusal) with `<project>/dist` as its root; the scope is the Deploy menu's. A blocked package opens the same dialog (title `Package blocked`); `commit` refuses it in main and never opens the save dialog.
- **Where:** after the gate passes, `commit` opens the native save dialog at `<project>/dist/<Name>-<version>.zip` (project name and version, characters Windows forbids replaced by `_`). `dist/` is git-ignored: `createProject` writes `.gitignore` (`build/`, `dist/`) and the samples carry the same file. A path inside a game `Data` folder is refused. Cancel writes nothing. The zip is written atomically (`<zip>.inkwell-tmp`, then rename).
- **Layout:** the files sit at the archive root exactly as in the MO2 mod folder (`Interface/exported/widgets/<modId>/<Widget>.swf`, `Scripts/*.pex`, `Source/Scripts/*.psc`, `<modId>.esp`, `textures/Inkwell/<modId>/*.dds` in dds mode, `Interface/Inkwell/<modId>/<Swf>.swf`, `SKSE/Plugins/Inkwell/menus/<menu>.json` and `SKSE/Plugins/Inkwell/<modId>.ini` for custom menus, never `Inkwell.ini`). No FOMOD, no `meta.ini`, no `.inkwell-deploy.json`. MO2 (Install a new mod from archive) and Vortex (Install From File) install such an archive as it is.
- **No README in the zip:** Vortex deploys every root file into the game's `Data` folder, so a `README.txt` would land there. Requirements (SKSE, SkyUI 5.2+) belong on the mod page.
- **Zip writer** (`zip.ts`, `node:zlib`, no dependency): deflate when smaller, else stored; CRC-32 (`zlib.crc32`); UTF-8 names (flag bit 11); entries sorted by name, fixed DOS timestamp 1980-01-01, no extra fields, no directory entries, no zip64 (refuses > 4 GB or > 65535 files). Two packages of the same input are byte-identical (the `.pex` compile timestamp aside, as for deploy).
- **Vortex:** Vortex keeps its staging folder as its own state (it hardlinks or moves files and tracks them), and a write into the game's `Data` folder is never allowed, so Inkwell writes nowhere inside Vortex. The `Vortex` row in the Deploy menu saves the same zip and the toast says how to install it (Mods > Install From File, then enable and deploy in Vortex). The `vortex` preset in `project.json` has no other effect.
- **Result:** a toast with the zip path, the file count, the gate warnings and an `Open folder` button (`revealPackage` IPC: main shows the last zip it wrote with `shell.showItemInFolder`; the renderer never passes a path). Progress and timing in the status bar like a deploy.
- Debug: `INKWELL_SHOTS_PACKAGE_DIR=<dir>` answers the save dialog with `<dir>\<Name>-<version>.zip` (screenshot runs; the setup driver then shoots `t-package-menu` (the Deploy menu with its Package Mod row), `u-package-done` or `u-package-blocked`, `v-vortex-menu`, `v-vortex-done`).

## Testing the runtime check (owner, in game)

Prepared folder: `Inkwell Menu Check Test` (the slice deployed with the Papyrus compiler; `TEST-IN-GAME-0.3.md`, test T4). Or by hand:

Deploy a menu mod (for example `yarn deploy:menu-slice` with `INKWELL_PAPYRUS` set) and enable the folder in MO2. (1) With `Inkwell.dll` present: no message. (2) Rename or remove `SKSE/Plugins/Inkwell.dll`, load a save (and start a new game): a message box says "<mod name> needs Inkwell Runtime 0.3.0 or newer, but it is not installed (or SKSE is not running)...". (3) Outdated: edit `Source/Scripts/<modId>_RuntimeCheck.psc` to `RequiredPacked = 262144` (0.4.0) and `RequiredText = "0.4.0"`, recompile it in place (`"D:\Mod Tools\Russo Compiler\papyrus.exe" compile -nocache -h "<editor>\resources\papyrus-stubs" -i "<mod>\Source\Scripts" -o "<mod>\Scripts"`), load: "needs Inkwell Runtime 0.4.0 or newer; you have 0.3.0". `Papyrus.0.log` shows a `[Inkwell] <modId>_RuntimeCheck: ...` line only in the failing cases; the plugin shows as light (ESL) in MO2.

## Known limits

- The runtime check plugin is hand-written (like the widget plugin), not opened in xEdit or the CK; whether a start-game-enabled quest of a plugin added to an EXISTING save needs a `.seq` file is unverified.
- The menu's lint summary and the status bar counts are the dock's (last sync builds); the gate itself uses what the deploy compiles, so they can differ before the first build. The dialog is the authority.
- There are no per-rule severity overrides (the design spec has none).

- `.pex` files embed a compile timestamp, so they are rewritten on every deploy even when nothing changed.
- Deploy uses the pipeline's resident FFDec wrapper; a build in progress queues behind it.
- Hot reload exists only with Dev deploy (`docs/dev-mode.md`). Installing the zip in real MO2 and Vortex is not tested yet.
